Lagos Emergency

01

The brief

Lagos is a city of roughly twenty million people and a road network that does not forgive hesitation. If you need an ambulance, the sequence is usually: find your phone, work out which number to call, hope you can describe where you are, and hope somebody on the other end can act on that description.

The premise of this project was narrow on purpose: reduce that sequence to a single tap. Not a directory of emergency services, not a form, not an account. One screen, three buttons, and the app works out the rest.

It was built under the Refcrypt Labs banner as a public-good project rather than a commercial one, and it is live and installable today.

02

Why offline-first was non-negotiable

Every emergency product has the same uncomfortable property: it is needed most at the exact moment the infrastructure around it is failing. Network congestion, a downed mast, a building with no signal — the scenarios where you need help are frequently the scenarios where you have no connection.

So the app assumes from the first line of code that the request will not reach a server. Tapping a button writes the alert to an IndexedDB queue and confirms immediately. The user sees that something happened. Synchronisation then becomes a background problem instead of a blocker.

The app shell itself is precached by a service worker, so the interface loads with no network at all — there is a dedicated offline fallback route rather than the browser's dinosaur.

03

How the queue actually works

Two mechanisms drain the queue, because browser support is not uniform:

  • Background Sync — the service worker listens for the sync event and replays queued alerts when the browser decides the connection is usable again.
  • The online event — a client-side listener does the same replay as a fallback for browsers without Background Sync support.

There is a /queue screen where the user can see exactly what is pending and trigger a manual sync, and an /offline shell so the app degrades visibly rather than silently.

The test I insist on: turn the network off properly — not throttled, off — tap a button, confirm the alert appears in the queue, then restore the connection and watch the queue drain. If you have not watched it empty, you have not tested it.

04

Routing when the sensor says no

Geolocation is a permission prompt, and permission prompts get denied. On tap the app requests the current position with a timeout; if the user refuses, or the fix fails, or the API is unavailable, the app does not stop.

It falls back to a dropdown of all twenty Lagos local government areas. Choosing one resolves the nearest police, fire and medical facilities for that area by distance, using haversine calculations against a local facility list — no API key, no server round trip, which matters precisely because the network is the thing that failed.

Facilities can also be found proactively on the /locate screen, which plots them on a Leaflet map with OpenStreetMap tiles. There is a reason that screen exists outside an emergency: nobody wants to discover a product's flaws while panicking.

05

Accessibility and the small screens

The entire flow is designed for one-handed use under stress. Buttons are large, colour-coded and labelled with text as well as colour, so the distinction does not depend on colour vision. The home screen is a single screen — there is no scroll and no navigation required to act.

The app is installable as a PWA with a manifest and icons, so it can live on the home screen next to the phone dialler rather than behind a browser and three taps.

06

What I would do differently

This project ships with documented gaps, and I would rather list them than let them be discovered:

  • The phone numbers in the constants file are placeholders. They need replacing with verified lines from each agency before this should be relied on. That is the single most important outstanding item.
  • The facility list should expand to all twenty LGAs. Coverage is uneven and routing quality depends directly on it.
  • The dispatch endpoint acknowledges and logs. POST /api/emergency currently accepts an alert and records it; wiring it to a real dispatch system — an agency API or an SMS gateway — is what turns this from a demonstration into infrastructure.
  • iOS needs a 180×180 touch icon before it installs cleanly on an iPhone.

The broader lesson I took from building it is about ambiguity in offline queues. A write can succeed on the server and fail on the way back, leaving the client unsure whether to retry. For an alert that triggers a dispatch, retrying twice could send two responders and not retrying could send none. No library resolves that for you — it is a product decision about which failure is worse, and it belongs written down rather than hidden in a callback.

What I am proudest of is not the technical machinery. It is that the response to “how do I get help” became a single tap.
