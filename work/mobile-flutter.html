01

Why Flutter for this work

The alternative to Flutter is either two native codebases or a web view, and neither is right for a small team shipping a real product. Two codebases means every feature is built twice and every bug is fixed twice. A web view means giving up on the things that make a mobile app worth installing in the first place.

Flutter gives one Dart codebase that compiles to native on both platforms, with a consistent rendering model rather than a thin wrapper over platform widgets. For a team of our size, halving the surface area is worth more than any single-platform advantage.

The trade-off is honest and worth stating: platform-specific behaviour still needs platform-specific code, and anyone who tells you otherwise has not shipped an app with background location or push notifications.

02

Architecture before features

The temptation on a mobile project is to start with the screens, because screens are what you can show somebody. The cost of that choice arrives about six months in, when every new feature requires understanding the whole app.

So I structure by feature rather than by layer: each feature owns its own presentation, logic and data access, and depends on shared abstractions rather than on other features. Adding a feature means adding a directory, not editing five.

The payoff is concrete. Onboarding a second developer is faster, tests stay local to the thing they test, and deleting a feature is a deletion rather than an archaeology exercise.

03

State management as a decision, not a default

State management is where Flutter projects most often go wrong, usually because a solution was adopted before the problem was understood. The question to answer first is not “which library” but “what kind of state is this”.

Server data that can be cached and needs to survive navigation is a different problem from ephemeral UI state, and different again from app-wide session state. Treating all three the same way produces either an anaemic app or an unmaintainable one.

I keep the rules explicit and consistent, so that a new screen's state has an obvious home and there is no argument about it in review. Consistency matters more here than picking the theoretically optimal tool.

04

The unglamorous mobile work

Most of the difficulty in a shipped mobile app is not in the feature list. It is in the parts that only appear on real devices on real networks:

  • Poor connectivity — requests that fail halfway, timeouts that need to be distinguished from genuine errors, and retries that must not duplicate a write.
  • Lifecycle — the app being backgrounded mid-request, or killed and restored, and what the user should see when that happens.
  • Permissions — camera, location and notifications, each of which can be refused, and none of which should be a dead end.
  • Release mechanics — signing, build flavours, versioning and the store submission path, which is where a surprising amount of project time quietly goes.

None of this is exciting and all of it determines whether the app feels reliable. Users do not distinguish between a feature that was never built and one that crashes when they open it.

05

What I would do differently

Two things I would change on the next mobile project.

First, I would set up automated device testing much earlier. Manual testing across a handful of physical devices does not scale, and the bugs that escape are predictably the ones involving interruption and resumption — the exact scenarios that manual testing does not naturally reproduce.

Second, I would instrument performance from the first internal build rather than after launch. Frame times, cold-start duration and memory behaviour are far easier to keep good than to make good retrospectively, and by the time a user complains about jank you have usually accumulated a dozen causes rather than one.

The broader lesson from this work is that cross-platform development rewards discipline more than cleverness. One codebase is a genuine advantage, and only if you resist the temptation to let it become two overlapping ones held together by conditionals.
