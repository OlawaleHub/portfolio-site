(02) — Method

Offline-first, in practice

The offline
playbook

01

Assume the request will fail

Every write in an offline-first app starts by assuming it will not reach the server. So the write goes to local storage first — in the emergency app, an IndexedDB queue — and the user gets confirmation immediately. The network is then a synchronisation problem, not a correctness problem.

The alternative, which most apps ship with, is a spinner and then an error message. That is a design decision as much as a technical one, and usually the wrong one.

02

Let the service worker do the retrying

The app shell is precached, so the interface loads with no connection at all. Queued writes are replayed on the browser's sync event, and also on the online event as a belt-and-braces fallback, because Background Sync support is not uniform across browsers.

One thing worth stating plainly: you cannot test offline mode by throttling in a tab and hoping. You have to toggle the network off properly, tap the thing, confirm it landed in the queue, and then come back online and watch it drain. If you have not watched the queue empty, you have not tested it.

03

Give people a way out when sensors fail

Geolocation is a permission prompt, and permission prompts get denied. In the emergency app, tapping a button tries GPS first, but if it is unavailable or refused, the user picks their local government area from a list of all twenty in Lagos and the nearest facility is resolved by area instead.

The lesson generalises: any feature that depends on a sensor or a permission needs a manual path beside it. The fallback is not a degraded experience — for some users it is the only experience they will ever have.

04

Decide what the queue does when it is ambiguous

A queued write can succeed on the server and fail on the way back. Now the client does not know whether to retry. For a report that triggers a dispatch, retrying twice could send two responders; not retrying could send none.

There is no clever library that resolves this for you. It has to be an explicit product decision about which failure is worse, and it has to be written down. In the emergency app that decision is documented in the README rather than buried in a callback.

(03) — Lessons

Earned the hard way

Things I
believe now

Ship the small version

The Lagos emergency app is deliberately one screen with three buttons. Every feature I considered adding — accounts, history, richer facility data — would have delayed the thing that matters, which is that a frightened person can get help in one tap. Scope is a safety property in some products.

Write the README for yourself in six months

Documenting the placeholder phone numbers and the unwired dispatch endpoint is not an admission of failure. It is the difference between the next person understanding the state of the system and quietly assuming it is production-ready.

Tests are a form of honesty

The governance contracts move tokens and issue refunds. Coverage there is not box-ticking; it is the only way I can credibly say a cancelled proposal will actually refund the people who paid to vote on it.

Accessibility is not a phase two

Semantic markup, keyboard navigation and contrast are cheaper to build in than to retrofit, and the people who benefit are not a niche. I would rather cut a feature than ship a form nobody can tab through.

Learn in public, imperfectly

Much of my early GitHub history is beginner CSS exercises with names like Practice-on-Html. I have left them up. A commit history that only shows polished work is not a history, it is a brochure.
